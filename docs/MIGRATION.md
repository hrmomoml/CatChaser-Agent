# 从当前 MuJoCo 动作到真机任务

## 明确选择

第一阶段走 **PC ROS 2播放器 → 主控官方 Interrupt → SDK → 电机**。本机不直接连接电机，保留主控的低层控制和策略平衡。该路径可以迁移手臂动作3～8；它没有腿部姿态接口，不能把1/2冒充已经迁移成功。

第二条已实现的接口是主控上的 **实验性23轴支撑调试桥接器**，用于有机械支撑时验证上下肢角度、方向和消息链路；它不提供双足平衡，也不能与官方推理同时占用CAN。

```mermaid
flowchart LR
    A[现有 RPO MuJoCo 动作] --> B[导出 23轴参考与10轴手臂 NPZ]
    B --> C[PC ROS 2 动作播放器]
    C --> D[/joint_ref_states 十轴绝对角度]
    D --> E[主控 Interrupt 策略]
    E --> F[robot_py对应的 C++ RobotInterface]
    F --> G[23个电机：策略控制下肢，外部参考控制双臂]
```

## 当前已有文件怎样使用

原程序 `rpo_description/cat_play/cat_play.py` 包含浮动基座、站蹲过渡、棒尖逆运动学、PD、隐式阻尼、重力和惯性前馈、踝姿态反馈。`motion_primitives.py` 定义动作3～8；1/2是姿态通道。

可以复用：动作时序、棒尖轨迹、关节名、IK生成的参考角度。需要替换：MuJoCo 状态读取和 `d.ctrl`；真机状态来自SDK/ROS，关节目标交给主控执行。仿真控制力矩、增益、隐式阻尼不直接导出到硬件。

运行导出：

```bash
/home/gyl/cat_agent_ws/.venv/bin/python scripts/export_motion.py --library
```

默认使用仓库内 `sim_source/` 的现有控制器快照和相邻的固定版本模型；换电脑可显式传 `--source`、`--repo`。导出依赖为 MuJoCo、numpy、PyYAML。

每个 `motion_3.npz`～`motion_8.npz` 包含：

| 数组 | 形状/含义 |
|---|---|
| `time_s` | N，起点0，50Hz采样 |
| `joint_names` | 23个逻辑关节名，与MJCF执行器顺序逐项核对 |
| `q_ref_full_source` | N×23，源仿真控制器参考角度 rad |
| `q_actual_source` | N×23，仿真实际关节角度，供跟踪误差分析 |
| `upper_joint_names` | 左5右5 |
| `upper_ref` | N×10，播放器使用的手臂角度；未动作的左臂保持官方默认值 |
| `upper_velocity` | N×10，参考角速度，供分析；官方JointState输入不使用此字段 |

同名JSON记录源模型/控制器SHA256、限位检查和 `hardware_validated=false`。这是**本项目播放器格式**，不是官方MotionLoader可直接读取的NPZ。NPZ本身不是可执行程序，不会自行控制电机。

对比样例：

```bash
/home/gyl/cat_agent_ws/.venv/bin/python scripts/export_motion.py --sequence '1+7 2+8'
```

浅蹲更新后，该样例的23轴参考均处于当前部署配置限位内；但`upper_only_compatible=false`，`whole_body_hardware_replay_allowed=false`。播放器不接收姿态组合命令，也不加载这类文件作为手臂动作。

| 阶段 | 做什么 | 验收 | 当前状态 |
|---|---|---|---|
| A | 源码对照、关节顺序、NPZ导出 | 23名字一致、角度有限、手臂不越部署配置限位 | 已完成 |
| B | ROS2模拟机器人联调 | 10轴命令、23轴反馈、服务、报文拒绝、断流处理 | 已完成 |
| C | 主控SDK编译和跨机DDS | 子模块锁定、补丁编译、网络端到端、读取真实反馈 | 无硬件，未完成 |

## 怎样迁移1、2以及姿态组合

1. **浅蹲参考已重新设计。** 双髋俯仰由-1.85改为-1.40rad，在官方-1.57rad下限内保留约0.17rad目标余量；膝1.55rad、踝俯仰-0.50rad、机身前倾0.35rad。髋部高度约0.57m。全部12种姿态/手臂组合以2ms步长检查23轴参考与实际值，未越配置限位、未跌倒。真实机构限位和增益仍需主控核对。
2. **确定脚踝连接件几何与运动关系。** 原始STL和细化碰撞体仍发现连接处相交；需要机械装配资料判断预期接触与建模简化，不能以关掉检测作为验收。
3. **补齐下肢闭环控制。** 优先训练/适配带目标高度或全身参考的RPO策略：将蹲/站目标和手臂参考纳入训练范围，让腿根据IMU、关节和支撑反馈维持平衡。保留只允许一个下肢控制器的结构。
4. **或采用全身动作跟踪。** 用合法的全身参考构建数据，训练对应的BeyondMimic式策略；不能假定官方已有wave/dance策略能跟踪任意新增动作。
5. **导出训练后模型并对齐接口。** 官方跟踪MotionLoader要求 `fps` 为int32、`joint_pos`/`joint_vel` 为float32 N×23。motion_command直接读取文件，未替你转换关节顺序，必须与训练的参考顺序一致。还需匹配的ONNX、观测布局、归一化、action_scale、usd2urdf等；只生成一个NPZ不够。
6. **先Sim2Sim再实机分级验证。** 合格后再为1/2建立项目ROS2服务或动作接口，使高层状态机发“站高/蹲高”目标，3～8发手臂参考。此接口属于待实现扩展，当前官方 `/cmd_vel` 和 `/joint_ref_states` 不能替代它。

如果只想在可靠机械支撑下逐个关节试运动，可以使用已提供的23轴SDK桥接；它通过 `apply_action` 控制上下肢，但并不解决自由站立或蹲起稳定性。参考 [DEPLOYMENT.md](DEPLOYMENT.md)。

## 关节、零位和增益

SDK 输入是23轴逻辑顺序：左腿0–5、右腿6–11、腰12、左臂13–17、右臂18–22。十轴手臂消息对应最后十项。政策输出顺序由usd2urdf转换，电机顺序由urdf2motor转换；这两种映射不能混为一谈。真实驱动方向、零位和并联解耦交给SDK处理。

部署配置给出的默认增益与源MuJoCo不同。现有软件不把仿真1200增益或qfrc_bias写到真机，也没有把仿真能站住当作实机验证。
